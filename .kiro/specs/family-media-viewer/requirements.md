# Requirements Document

## Introduction

A read-only media viewer for a family's S3-stored video collection (5600+ files, growing). The application provides date-based browsing with thumbnail grids, video playback with transcript display, and metadata viewing. The architecture supports a future image phase (separate S3 bucket, same app) and future metadata editing (specifically the `description` field) that will feed a Bedrock knowledge base ingestion pipeline. Authentication is simple username/password for approximately 20 admin-managed accounts, with credentials stored in DynamoDB.

## Glossary

- **Viewer**: The React frontend single-page application
- **API**: The FastAPI backend service
- **Media_Item**: A single video (or future image) with its associated metadata, transcript, and thumbnail files
- **Media_Bucket**: An S3 bucket containing media files organized by year folders (e.g., `2014/`, `2020/`, `unknown_year/`)
- **Metadata_File**: A JSON file in Bedrock KB metadata format stored alongside each media file (`{id}.mp4.metadata.json`), containing a top-level `metadataAttributes` object
- **Transcript_File**: A markdown file containing the transcript for a video (`{id}.md`)
- **Thumbnail_File**: A JPEG image stored alongside the video in S3 (`{id}.jpg`), pre-generated by an external pipeline
- **Media_Type**: A classification of media — currently `video`, with `image` planned for a future phase
- **Year_Folder**: A top-level S3 prefix representing the year a media item was created (e.g., `2014/`, `unknown_year/`)
- **Presigned_URL**: A time-limited S3 URL that grants temporary read access to a specific object without exposing AWS credentials
- **Auth_Session**: An authenticated user session maintained via a session token after successful login
- **Metadata_Schema**: The structured shape of metadata fields within `metadataAttributes`, designed to be compatible with future Bedrock KB write-back and ingestion pipeline updates
- **User_Table**: A DynamoDB table storing user credentials (username, bcrypt-hashed password)

## Requirements

### Requirement 1: User Authentication

**User Story:** As a family member, I want to log in with a username and password, so that only authorized users can access the media collection.

#### Acceptance Criteria

1. WHEN a user submits valid credentials, THE API SHALL verify the password against the bcrypt hash stored in the User_Table and return a session token, and THE Viewer SHALL store the token for subsequent requests
2. WHEN a user submits invalid credentials, THE API SHALL return an authentication error with no detail about which field was incorrect
3. WHILE no valid Auth_Session exists, THE Viewer SHALL redirect all navigation to the login page
4. WHEN a user clicks the logout button, THE Viewer SHALL clear the Auth_Session and redirect to the login page
5. IF an API request is made with an expired or invalid session token, THEN THE API SHALL return a 401 status code
6. THE API SHALL store user credentials in the User_Table with passwords hashed using bcrypt
7. THE API SHALL provide a CLI command or admin API endpoint that creates a new user record in the User_Table with a username and bcrypt-hashed password
8. THE Viewer SHALL NOT provide a self-service sign-up flow; user accounts are created exclusively by an administrator via the CLI command or admin API endpoint

### Requirement 2: Media Listing by Date

**User Story:** As a family member, I want to browse media organized by year as a thumbnail grid, so that I can find videos from a specific time period.

#### Acceptance Criteria

1. WHEN an authenticated user navigates to the main view, THE Viewer SHALL display Media_Items grouped by Year_Folder in reverse chronological order
2. THE API SHALL read Year_Folder prefixes from the configured Media_Bucket and return them as a list of available years
3. WHEN a user selects a Year_Folder, THE API SHALL return a paginated list of Media_Items within that folder
4. THE Viewer SHALL display Media_Items within each Year_Folder group as a thumbnail grid
5. THE Viewer SHALL display a Media_Type filter tab that filters the listing to show only items of the selected type, or all items when no filter is active
6. THE Viewer SHALL enable only the `video` filter tab at launch, with additional Media_Type tabs rendered as disabled
7. WHEN the Media_Bucket contains a folder named `unknown_year`, THE Viewer SHALL display that group after all dated Year_Folders
8. IF the API cannot reach the Media_Bucket, THEN THE API SHALL return a 503 status code with a descriptive error message


### Requirement 3: Thumbnail Display

**User Story:** As a family member, I want to see thumbnail previews of videos in the browse view, so that I can visually identify content before clicking.

#### Acceptance Criteria

1. WHEN the API returns a list of Media_Items, THE API SHALL check for a Thumbnail_File (`{id}.jpg`) alongside each video in the Media_Bucket and include a Presigned_URL for the thumbnail if the file exists
2. WHEN a Thumbnail_File exists for a Media_Item, THE Viewer SHALL display the thumbnail image in the grid listing
3. WHEN no Thumbnail_File exists for a Media_Item, THE Viewer SHALL display a placeholder image in the grid listing
4. THE API SHALL NOT generate thumbnails; Thumbnail_Files are pre-generated by an external pipeline and stored in the Media_Bucket
5. WHERE the Media_Type is `image` (future phase), THE Viewer SHALL use a resized version of the image itself as the thumbnail

### Requirement 4: Video Playback

**User Story:** As a family member, I want to play a video from the collection, so that I can watch family memories.

#### Acceptance Criteria

1. WHEN a user selects a Media_Item of type `video`, THE API SHALL generate a Presigned_URL for the corresponding `.mp4` file in the Media_Bucket
2. THE API SHALL generate Presigned_URLs with an expiration time of no more than 1 hour
3. WHEN the Viewer receives a Presigned_URL, THE Viewer SHALL render an HTML5 video player with standard playback controls (play, pause, seek, volume)
4. IF the Presigned_URL has expired during playback, THEN THE Viewer SHALL request a new Presigned_URL from the API and resume playback
5. IF the requested video file does not exist in the Media_Bucket, THEN THE API SHALL return a 404 status code

### Requirement 5: Transcript Display

**User Story:** As a family member, I want to read the transcript alongside a video, so that I can follow along or search the content.

#### Acceptance Criteria

1. WHEN a user views a Media_Item that has an associated Transcript_File, THE API SHALL return the transcript content as markdown text
2. THE Viewer SHALL render the transcript as formatted markdown in a panel adjacent to the video player
3. WHEN a Media_Item has no associated Transcript_File, THE Viewer SHALL display a "No transcript available" message in the transcript panel
4. IF the Transcript_File cannot be read from the Media_Bucket, THEN THE API SHALL return the Media_Item detail without transcript content and include an error indicator for the transcript field

### Requirement 6: Metadata Display

**User Story:** As a family member, I want to view metadata about a video, so that I can see details like date, description, and playlists.

#### Acceptance Criteria

1. WHEN a user views a Media_Item, THE API SHALL read the associated Metadata_File and return the `metadataAttributes` object, which contains the fields: `video_id`, `title`, `url`, `upload_date` (YYYYMMDD string), `playlists`, `transcript_language`, `processed_timestamp` (ISO 8601), and `description`
2. THE Viewer SHALL render metadata fields in a readable format in the media detail view
3. WHEN a Media_Item has no associated Metadata_File, THE Viewer SHALL display a "No metadata available" message
4. THE API SHALL treat the `upload_date` field as a YYYYMMDD string for sorting and display purposes, not as an ISO date
5. THE API SHALL use the `url` field to store the S3 Presigned_URL for the media file in the API response context
6. IF the Metadata_File contains fields not defined in the current Metadata_Schema, THEN THE API SHALL preserve those fields in the response without discarding them
7. THE API SHALL treat the `playlists` field as optional; WHEN the field is blank or empty, THE Viewer SHALL omit it from the display

### Requirement 7: Metadata Editing Stub

**User Story:** As a family member, I want to see where metadata editing will be available, so that I understand the application will support editing the description field in the future.

#### Acceptance Criteria

1. THE Viewer SHALL display a disabled "Edit Description" control on the media detail view, adjacent to the `description` field
2. WHEN a user interacts with the disabled edit control, THE Viewer SHALL display a message indicating that description editing is planned for a future release
3. THE API SHALL expose a metadata update endpoint that accepts a Media_Item identifier and a partial payload containing the `description` field, and returns a 501 (Not Implemented) status code
4. THE API metadata update endpoint SHALL validate that the incoming payload contains a `description` string field before returning the 501 response, so that the contract is exercised and tested before implementation
5. THE Metadata_Schema SHALL include a `last_modified_by` field and a `schema_version` field to support future audit trail and Bedrock KB ingestion pipeline compatibility

### Requirement 8: Sort Mode Stubs

**User Story:** As a family member, I want to see that additional sort options are planned, so that I know the application will support more ways to browse media.

#### Acceptance Criteria

1. THE Viewer SHALL display sort mode options (e.g., "By Date", "By Name", "By Duration") with only "By Date" enabled
2. WHEN a user interacts with a disabled sort mode option, THE Viewer SHALL display a message indicating that the sort mode is planned for a future release
3. THE API SHALL expose a sort parameter on the media listing endpoint that currently accepts only `date` as a valid value
4. IF the API receives an unsupported sort parameter value, THEN THE API SHALL return a 400 status code with a message listing the currently supported sort values

### Requirement 9: Multi-Bucket Media Type Configuration

**User Story:** As a developer, I want the backend to support multiple S3 bucket configurations per media type, so that adding image support later requires only configuration changes and a new viewer component.

#### Acceptance Criteria

1. THE API SHALL read media source configuration from a structured config that maps each Media_Type to a Media_Bucket name and file extension pattern
2. THE API SHALL support at minimum one configured Media_Type (`video`) at launch
3. WHEN a new Media_Type is added to the configuration, THE API SHALL serve listing and detail endpoints for that type without code changes to the routing or S3 access layer
4. THE API media source configuration SHALL include fields for: bucket name, file extension pattern, metadata file suffix pattern, thumbnail file suffix pattern, and optional transcript file suffix pattern

### Requirement 10: Application Deployment

**User Story:** As a developer, I want to deploy the application as a Docker container on a single EC2 instance, so that infrastructure complexity matches the small user base.

#### Acceptance Criteria

1. THE API and Viewer SHALL be packaged into a single Docker image that serves both the backend API and the frontend static assets
2. THE Docker image SHALL accept configuration via environment variables for: S3 bucket names, AWS region, session secret, and DynamoDB table name
3. WHEN the Docker container starts, THE API SHALL perform a health check that verifies S3 connectivity and DynamoDB connectivity and return the result on a `/health` endpoint
4. IF the health check fails, THEN THE API SHALL return a 503 status code on the `/health` endpoint with a description of which dependency is unreachable
